# 15 · Files & Data

> Moving bytes looks trivial until someone uploads a 4 GB video, a CSV with 10 million rows or a
> file called `../../etc/passwd`. **The rule that governs everything: your backend shouldn't touch the bytes
> if it can avoid it.**


**Covers from the syllabus:** `uploads` · `storage` · `processing` · `streaming` · `security` · `failure_modes`

---

## The right pattern: presigned URLs

**Wrong:** client → your server → S3. Your app eats the bandwidth, the memory and the request time.
A 2 GB file ties up a worker for minutes.

**Right:**
```
1. Client asks for permission        → POST /uploads  {name, type, size}
2. Your backend validates and signs  → returns a presigned URL (PUT) + an upload_id
3. Client uploads DIRECTLY to S3     → PUT https://bucket.s3.../abc?X-Amz-Signature=...
4. Client notifies                   → POST /uploads/{id}/complete
   (or better: S3 emits an event and your backend reacts)
```

**What you validate when signing (step 2), which is where the real security lives:**
- That the user has permission and available quota.
- **Maximum size**, with `content-length-range` in the signature policy (otherwise they upload 50 GB).
- **Allowed content type**, included in the signature.
- **You generate the object key** (`tenant/{id}/uploads/{uuid}.jpg`) — **never use the name the client
  sends**: that's path traversal and overwriting other people's files.
- **Short expiry** on the URL (minutes).

**For downloads**, the same: a read presigned URL with an expiry, instead of proxying gigabytes. If
you need per-request access control, sign the URL **after** checking permissions.

> **Card** · **When:** any file upload or download ·
> **Pattern:** the backend only validates and signs; the bytes go straight to object storage ·
> **Anti-pattern:** proxying gigabytes through your application ·
> **Limits:** the signature must include `content-length-range` and the type, or they upload 50 GB ·
> **How it fails:** using the client's name as the key enables path traversal and overwriting other people's files ·
> **Decision:** the object key **is generated by the server** (`tenant/{id}/uploads/{uuid}`) ·
> **Trade-off:** control (proxy) vs scalability (direct) ·
> **Related:** object storage, validation `[13]`

## Multipart and resumable uploads

For large files (>100 MB) or unstable networks:

1. `CreateMultipartUpload` → returns an `uploadId`.
2. Upload the parts (minimum 5 MB each except the last one), **in parallel**, each with its own ETag.
3. `CompleteMultipartUpload` with the list of parts.

**Advantages:** you retry **only the failed part**, you upload in parallel (much faster), and you can pause and
resume.

**The operational detail people forget:** **incomplete** multipart uploads **keep taking up and billing for**
invisible space. Configure a *lifecycle rule* that aborts them after N days. It's a classic hidden cost.

> **Card** · **When:** large files or unstable networks ·
> **Pattern:** split into parts, upload in parallel, retry only the failed part ·
> **Anti-pattern:** retrying the whole upload after the connection drops at 90% ·
> **Limits:** minimum 5 MB per part except the last one ·
> **How it fails:** **incomplete** multipart uploads **keep billing** for invisible space ·
> **Decision:** a lifecycle rule that aborts incomplete uploads after N days ·
> **Trade-off:** client complexity vs robustness and speed ·
> **Related:** cost, object storage `[13]`

## File validation and security

**Never trust:**
- **The extension.** `photo.jpg` can be an executable.
- **The `Content-Type` the client sends.** It's a header; it can be forged.
- **The file name.** Path traversal (`../../`), null characters, Windows reserved names
  (`CON`, `PRN`), deceptive unicode, absurd lengths.

**Do:**
- **Check the magic bytes** (the first bytes of the file) with a type-detection library, and
  verify they match what you claim to accept.
- **Always rename** to an identifier you generate; keep the original name only as metadata for
  display.
- **Size limits** in the signature, in the proxy and in the application.
- **Serve from a different domain** (or a dedicated cookieless subdomain) with `Content-Disposition: attachment`
  and `X-Content-Type-Options: nosniff`. Serving uploaded content from your main domain is **stored XSS
  on steroids**: an uploaded SVG or HTML file runs JavaScript with your cookies.
- **Be careful with SVGs:** they're XML and can contain scripts. Sanitize them or convert them to raster.
- **Zip bombs:** a 1 MB zip can decompress into 1 TB. Limit the ratio and the decompressed size.
- **XXE:** when parsing user-supplied XML, disable external entities or you expose local files and open the door to SSRF.

**Virus scanning:** ClamAV (open source) or the cloud providers' services. The usual pattern is **quarantine**:
upload to an isolated bucket → scan asynchronously → move to the final bucket only if it's clean. The
file isn't accessible in the meantime. Mandatory if users share files with each other.

> **Card** · **When:** every file a user uploads ·
> **Pattern:** magic bytes + size and dimension limits + always rename ·
> **Anti-pattern:** trusting the extension or the `Content-Type` ·
> **Limits:** detecting the real type doesn't guarantee the content is harmless ·
> **How it fails:** an SVG or HTML file served from your domain is **stored XSS** with your cookies `[06]` ·
> **Decision:** serve from another domain, with `attachment` and `nosniff` ·
> **Trade-off:** restricting formats vs flexibility for the user ·
> **Related:** XSS, headers, antivirus `[02, 06]`

## Image and video processing

**Images:**
- **Never in the request.** Resizing is CPU and memory: it goes to a queue (`08-distributed-systems.md`).
- **Generate derivatives** (thumbnail, medium, large) and serve them through a CDN. Modern formats: WebP and AVIF with
  a fallback.
- **"Decompression bomb" limits**: a 50,000×50,000-pixel image takes up gigabytes once
  decompressed, even if the file itself is small. Validate dimensions **before** processing.
- **Strip EXIF metadata** before serving: it contains **GPS coordinates**, camera model and date.
  It's a real and frequent privacy leak.
- Alternative: an on-demand transformation service (imgproxy, Cloudinary) with signed URLs —
  less storage and more flexibility.

**Video:**
- **Transcoding** to several resolutions and bitrates (far more expensive than images). A dedicated queue, or a
  managed service (MediaConvert, Mux).
- **Adaptive streaming** (HLS/DASH): the video is split into segments and the player picks the quality based on the
  available bandwidth. You don't serve one giant MP4.
- **Design for long-running jobs:** queryable progress, resumable, with a generous timeout and a notification when
  it finishes (webhook or SSE to the client).

> **Card** · **When:** any media uploaded by users ·
> **Pattern:** in a queue, never in the request; derivatives served through a CDN ·
> **Anti-pattern:** resizing inside the HTTP handler ·
> **Limits:** a 50,000×50,000 image takes up gigabytes once decompressed, even if the file is small ·
> **How it fails:** **EXIF metadata carries GPS coordinates**: a privacy leak when you serve it ·
> **Decision:** validate dimensions **before** processing; always strip EXIF ·
> **Trade-off:** pre-generating derivatives (storage) vs transforming on demand (CPU and latency) ·
> **Related:** background jobs, CDN `[09]`

## CSV, Excel and exports

**Importing:**
- **Always stream.** Reading a 2 GB CSV with `read()` is a guaranteed OOM. Process row by row or in
  batches.
- **Validate and report per row**: don't abort everything because of an error on row 8,432. Return an error
  report with line number and reason, and decide the policy (all or nothing / partial with a report).
- **Process in the background** with progress. A 500,000-row import doesn't fit in an HTTP request.
- **Idempotency:** if the user uploads the same file twice, don't create duplicates. File hash + a natural key
  per row.
- **Encoding traps:** UTF-8 with and without BOM, Latin-1, `;` separators in European Excel, line breaks
  inside quoted fields. Use a real CSV library, **never `split(",")`**.

**Exporting:**
- **Stream** the response with a server-side cursor, instead of loading everything into memory.
- If it's large: generate it asynchronously into S3 and send a link by email or notification.

**CSV injection (a vulnerability almost nobody knows about):** if a field starts with `=`, `+`, `-` or `@`,
Excel interprets it as a formula and can execute commands when the file is opened. **Escape it by prefixing an apostrophe**
in exports. It has caused real incidents of code execution on users' machines.

> **Card** · **When:** data imports and exports ·
> **Pattern:** streaming in both directions, in batches, with a per-row error report ·
> **Anti-pattern:** `split(",")` instead of a CSV library, and loading the whole file into memory ·
> **Limits:** encodings (BOM, Latin-1), European Excel's `;` separators, line breaks inside quotes ·
> **How it fails:** **CSV injection** — a field starting with `=` runs as a formula when the file is opened ·
> **Decision:** abort everything or import partially with a report: decide it and document it ·
> **Trade-off:** strict validation vs tolerance for real-world dirty data ·
> **Related:** background jobs, idempotency `[08]`

## PDFs

- **Generation:** from HTML (Puppeteer/Playwright/WeasyPrint — easier to lay out) or with libraries
  (ReportLab). It's **CPU-intensive and slow**: it goes to a queue, not into the request.
- **Puppeteer in production:** it opens an entire browser per document. Limit concurrency, reuse the
  browser, and give it a timeout — it's a classic source of memory leaks and dead containers.
- **If the HTML includes user data**, an `<img src="http://169.254.169.254/...">` inside the document
  gives an attacker **SSRF** from the renderer. Disable network access or restrict it with an allowlist.
- **Reading PDFs** (text/table extraction) is notoriously unreliable: scanned PDFs need OCR
  (Tesseract or cloud services). Don't promise accuracy without testing against real documents.

> **Card** · **When:** invoices, reports, contracts ·
> **Pattern:** generate in a queue, with a timeout and limited concurrency ·
> **Anti-pattern:** opening a headless browser per document inside the request ·
> **Limits:** text extraction is unreliable; scanned documents need OCR ·
> **How it fails:** an `<img src="http://169.254.169.254/...">` in the HTML gives **SSRF** from the renderer `[06]` ·
> **Decision:** disable the renderer's network access or restrict it with an allowlist ·
> **Trade-off:** HTML (easy to lay out, heavy) vs libraries (fast, rigid) ·
> **Related:** SSRF, background jobs `[06]`

## Background processing

Everything in this box ends up here. **Rule: if it takes more than ~1 second or can fail, it doesn't belong in the request.**

```
POST /reports   →  202 Accepted + {job_id, status_url}
                   enqueues the job
GET /jobs/{id}  →  {status: "processing", progress: 45}
                → {status: "ready", download_url: "..."}
```

- **Job state in the database**: pending → processing → completed / failed, with progress,
  result, error and timestamps.
- **Idempotency and retries** (`08-distributed-systems.md`): a worker can die halfway through and the message
  gets redelivered. The job must be resumable or repeatable without duplicating effects.
- **Separate queues by type and priority** (bulkheads): so a 2-hour import doesn't block sending
  verification emails.
- **Visibility:** progress for the user, and queue depth and oldest-message-age metrics
  for you.
- **Cleanup:** temporary files, old jobs and expired results. A full disk is a surprisingly frequent
  cause of incidents.

> **Card** · **When:** anything that takes more than ~1 second or can fail ·
> **Pattern:** 202 + `job_id` + queryable status; separate queues by priority ·
> **Anti-pattern:** generating a report inside the HTTP request ·
> **Limits:** the worker can die halfway through: the job must be resumable or repeatable ·
> **How it fails:** a 2-hour import blocks the verification-email queue ·
> **Decision:** bulkheads — one queue per job type `[10]` ·
> **Trade-off:** complexity (state, progress, cleanup) vs an immediate response to the user ·
> **Related:** queues, idempotency, bulkheads `[08, 10]`

## Retention, privacy and lifecycle

- **Lifecycle rules** to move data to cheaper storage classes and delete what has expired: among the most
  profitable cost optimizations there are.
- **GDPR and deletion:** the right to be forgotten clashes with backups and with accounting obligations
  (`07-payments.md`). The usual solution is to **anonymize** the personal data while keeping the
  financial record, and to document the retention periods.
- **Encryption at rest** by default, and field-level encryption for what's truly sensitive.
- **Versioning and object lock** as a defence against accidental deletions and ransomware.
- **Never use real production data in development.** Anonymize it or generate synthetic data.

> **Card** · **When:** when defining what gets stored and for how long ·
> **Pattern:** lifecycle rules + encryption at rest + versioning with object lock ·
> **Anti-pattern:** keeping everything forever, just in case ·
> **Limits:** the GDPR right to erasure clashes with mandatory accounting retention ·
> **How it fails:** backups keep data you thought you had deleted ·
> **Decision:** anonymize personal data while keeping the financial record `[07]` ·
> **Trade-off:** cost and legal risk of keeping data vs the value of historical data ·
> **Related:** compliance, cost, backups `[06, 13]`

## Failure modes: file handling

| Failure | Cause | Mitigation |
|---|---|---|
| **Interrupted upload** | unstable network, large file | resumable multipart |
| **Orphaned multipart** | the client gave up | lifecycle rule that aborts after N days |
| **Corrupt file** | cut off halfway, or altered bytes | **client-side checksum** (`Content-MD5`/SHA-256) verified on completion |
| **Spoofed type** | the extension was trusted | magic bytes |
| **Stored XSS** | HTML/SVG served from your domain | separate domain + `attachment` + `nosniff` |
| **Zip bomb** | 1 MB that decompresses into 1 TB | limits on ratio and decompressed size |
| **Image bomb** | huge dimensions in a small file | validate dimensions before processing |
| **Path traversal** | the client's name used as the key | server-generated key |
| **Disk full** | temp files never cleaned up | cleanup and quotas; process as a stream |
| **OOM while processing** | whole file loaded into memory | batched streaming |
| **Orphans** | the DB record failed after the upload | reconciliation job that deletes whatever nothing references |
| **Broken reference** | the object was deleted but not the row | two-phase deletion with a pending flag |

**The most forgotten case: consistency between the file and its record.** Uploading to S3 and saving to the
database are **two writes to two systems** — the same dual-write problem the outbox solves
(`[08]`). The practical pattern: create the row as `pending` → upload → mark it `ready`; plus a
periodic job that cleans up old `pending` rows and objects that have no row.

```python
async def complete_upload(upload_id: str, actor: User):
    record = await repo.uploads.get(upload_id, tenant_id=actor.tenant_id)
    meta = await s3.head_object(Bucket=BUCKET, Key=record.key)     # does it actually exist?

    if meta["ContentLength"] != record.declared_size:
        raise InconsistentFile()
    if meta["ChecksumSHA256"] != record.declared_checksum:          # real integrity check
        await s3.delete_object(Bucket=BUCKET, Key=record.key)
        raise CorruptFile()

    await repo.uploads.mark_ready(upload_id)      # only now is it visible to the user
    await queue.enqueue("process_file", upload_id)
```

> **Card** · **When:** every upload that has a record in the database ·
> **Pattern:** pending → upload → verify (size and checksum) → ready, plus a cleanup job ·
> **Anti-pattern:** marking the file as available before checking that it arrived in full ·
> **Limits:** you can't guarantee atomicity between object storage and the database ·
> **How it fails:** orphans in both directions — objects without a row and rows without an object ·
> **Decision:** the `pending` state is what makes the inconsistency reconcilable ·
> **Trade-off:** an extra step and a cleanup job in exchange for not piling up garbage or broken links ·
> **Related:** outbox, reconciliation, cost `[07, 08, 13]`

## Interview questions and trade-offs

**Q: Design uploads for files of up to 5 GB.**
A presigned multipart upload straight to S3; the backend only validates permissions, quota, type and size when signing, and
reacts to the completion event. *Signal:* you mention that the backend must not proxy the bytes, aborting
incomplete multipart uploads, and that the server generates the object key.

**Q: How do you validate that a file really is an image?**
Magic bytes with a detection library, maximum dimensions, and re-encoding/normalization. *Signal:*
you say that neither the extension nor the `Content-Type` is good enough, and you mention decompression bombs and the problem
of SVGs carrying scripts.

**Q: Why not serve uploaded files from your main domain?**
Because an uploaded HTML or SVG file would run JavaScript with access to your domain's cookies. *Signal:* you cite
`Content-Disposition: attachment`, `nosniff` and the separate domain, and you call it by its name: stored XSS.

**Q: A user uploads a 2 GB CSV with 10 million rows. How do you process it?**
Direct upload to object storage, a background job, streaming reads in batches, per-row validation with
an error report, queryable progress and idempotency by hash. *Signal:* you bring up encoding and
separators as the real problem that eats the most time in practice.

**Q: What is CSV injection?**
A field starting with `=` gets executed as a formula when the file is opened in Excel. It's mitigated by escaping
the prefix. *Signal:* knowing about it is the signal in itself — it's a vulnerability that's almost always overlooked, and it
shows you think about the data's full lifecycle, not just about your API.

**Core trade-off of this box:** *control vs cost and scalability*. The more the bytes pass through your
application, the more control you have (immediate validation, transformation, fine-grained authorization) and the worse you scale.
The senior stance is to **delegate transport to object storage and the CDN**, and keep what really is yours:
permissions, validation, metadata and orchestration of the processing.
