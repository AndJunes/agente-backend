# Internacionalización (i18n)

Mirag viene en **inglés** y **español**. Cada locale es una carpeta, y un locale solo está
completo cuando existen todos sus recursos:

```
src/mirag/
├── locales/
│   ├── en/
│   │   ├── messages.json   textos del backend: resúmenes de etapas, respuestas, avisos, errores
│   │   ├── ui.json         todos los textos de la página web
│   │   ├── lexicon.json    heurísticas de idioma: patrones de intención, stop words, sinónimos
│   │   └── corpus.json     los marcadores del corpus de conocimiento en inglés
│   └── es/                 los mismos cuatro archivos, en español
└── knowledge/
    ├── en/                 las 19 cajas de conocimiento en inglés
    └── es/                 las 19 cajas de conocimiento en español (la edición original)
```

## Cómo se resuelve el locale de un request

1. El `locale` explícito del request (body de `POST /api/v1/chat`, query `?locale=`).
2. El header `Accept-Language` (`es-AR,es;q=0.9` → `es`).
3. `MIRAG_LOCALE` (por defecto `en`).

El locale selecciona **todo** para ese request: el corpus de conocimiento en el que se busca, el
léxico que se usa para detectar la intención (`Creá una API` y `Create an API` son, las dos,
pedidos de código), el catálogo que se usa para cada mensaje y la directiva de idioma que se le
envía al modelo. Dos requests en idiomas distintos pueden correr de forma concurrente: cada
locale tiene su propio `RetrievalEngine` cacheado.

## Mensajes

`messages.json` es un objeto JSON anidado; el código hace referencia a claves con puntos:

```python
catalog = i18n.catalog("es")
catalog.t("pipeline.context.summary", tokens="3,822", included=12)
# '~3,822 tokens · 12 trozos'
```

Los parámetros que faltan quedan visibles (`{name}`) en lugar de lanzar una excepción: una
traducción faltante nunca debe tirar abajo una respuesta que ya costó dinero. Las claves que
faltan caen al inglés, y si tampoco están, a la propia clave.

## El léxico

Las decisiones deterministas dependen del idioma del texto, así que son datos:

| Sección | Usada por |
|---|---|
| `intent.*` | `IntentClassifier` - ¿el request pide código, un proyecto, símbolos, relaciones, profundidad? |
| `stopwords.*` | suficiencia, obligaciones, búsqueda de símbolos y el árbol de conocimiento experimental |
| `inflection_suffixes` | suficiencia: una palabra ausente que parece flexionada es idioma, no un tema |
| `subdomain_synonyms` | metadatos: puente entre las subcategorías del temario y las palabras del corpus |
| `code_synonyms` | búsqueda de símbolos: de palabras de la consulta a identificadores de código (`validar` → `validate`) |
| `project_state.*` | el atajo de self-knowledge y su guarda contra órdenes de trabajo |
| `claims.*` | `ClaimAuditor` - cómo se ve una afirmación de éxito y cómo se ve una salvedad honesta |
| `demos.*` | reconocer las demos offline preparadas |
| `model_routing.*` | el router de modelos experimental |

## El formato del corpus

El parser del corpus no tiene idioma propio. `corpus.json` le indica los marcadores:

| Campo | Inglés | Español |
|---|---|---|
| marcador de ficha | `Card` | `Ficha` |
| campos | When, Pattern, Anti-pattern, Limits, How it fails, Decision, Depends on, Trade-off, Related | Cuándo, Patrón, Anti-patrón, Límites, Cómo falla, Decisión, Depende de, Trade-off, Relacionado |
| secciones de fallos | `Failure modes…`, `Failure scenarios…`, `Business inconsistencies…` | `Cómo falla…`, `Escenarios de fallo…`, `Inconsistencias de negocio…` |
| sección de fuentes | `Sources` | `Fuentes` |
| línea del temario | `Covers from the syllabus` | `Cubre del temario` |

Los dos corpus tienen las mismas cajas, las mismas secciones `##` en el mismo orden, la misma
cantidad de fichas, entradas de fallos y anti-patrones, y referencias cruzadas idénticas
(`` `[04, 09]` ``). Los tests de retrieval verifican esa paridad.

## La página web

`GET /api/v1/i18n/{locale}` sirve `ui.json`; la página renderiza todo el texto estático mediante
atributos `data-i18n` y todo el texto dinámico mediante un helper `t(key, params)`. El selector
de idioma guarda la elección en `localStorage` y la envía con cada request de chat.

## Agregar un locale

1. Copiar `locales/en` a `locales/<xx>` y traducir los cuatro archivos (manteniendo claves y
   placeholders).
2. Traducir `knowledge/en` a `knowledge/<xx>`, manteniendo la estructura y los marcadores
   declarados en `corpus.json`.
3. Agregar `"<xx>"` a `SUPPORTED_LOCALES` en `mirag/i18n/registry.py`.
4. Correr `make test`: los tests de paridad listan todo lo que falta.
