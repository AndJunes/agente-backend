# Internationalisation (i18n)

Mirag ships in **English** and **Spanish**. Each locale is a folder, and a locale is complete
only when all of its resources exist:

```
src/mirag/
├── locales/
│   ├── en/
│   │   ├── messages.json   backend strings: step summaries, answers, warnings, errors
│   │   ├── ui.json         every string of the web page
│   │   ├── lexicon.json    language heuristics: intent patterns, stop words, synonyms
│   │   └── corpus.json     the markers of the English knowledge corpus
│   └── es/                 the same four files, in Spanish
└── knowledge/
    ├── en/                 the 19 knowledge boxes in English
    └── es/                 the 19 knowledge boxes in Spanish (the original edition)
```

## How a request gets its locale

1. The explicit `locale` of the request (`POST /api/v1/chat` body, `?locale=` query).
2. The `Accept-Language` header (`es-AR,es;q=0.9` → `es`).
3. `MIRAG_LOCALE` (default `en`).

The locale selects **everything** for that request: the knowledge corpus that is searched, the
lexicon used to detect intent (`Creá una API` and `Create an API` are both code requests), the
catalog used for every message, and the language directive sent to the model. Two requests in
different languages can run concurrently: each locale has its own cached `RetrievalEngine`.

## Messages

`messages.json` is a nested JSON object; code refers to dotted keys:

```python
catalog = i18n.catalog("es")
catalog.t("pipeline.context.summary", tokens="3,822", included=12)
# '~3,822 tokens · 12 trozos'
```

Missing parameters stay visible (`{name}`) instead of raising: a missing translation must never
take down an answer that already cost money. Missing keys fall back to English, then to the key.

## The lexicon

Deterministic decisions depend on the language of the text, so they are data:

| Section | Used by |
|---|---|
| `intent.*` | `IntentClassifier` - does the request ask for code, a project, symbols, relationships, depth? |
| `stopwords.*` | sufficiency, obligations, symbol search and the experimental knowledge tree |
| `inflection_suffixes` | sufficiency: an absent word that looks inflected is language, not a topic |
| `subdomain_synonyms` | metadata: bridge from syllabus subcategories to words of the corpus |
| `code_synonyms` | symbol search: query words to code identifiers (`validar` → `validate`) |
| `project_state.*` | the self-knowledge shortcut and its work-order guard |
| `claims.*` | `ClaimAuditor` - what a success claim looks like, and what an honest caveat looks like |
| `demos.*` | recognising the prepared offline demos |
| `model_routing.*` | the experimental model router |

## The corpus format

The corpus parser has no language of its own. `corpus.json` tells it the markers:

| Field | English | Spanish |
|---|---|---|
| card marker | `Card` | `Ficha` |
| fields | When, Pattern, Anti-pattern, Limits, How it fails, Decision, Depends on, Trade-off, Related | Cuándo, Patrón, Anti-patrón, Límites, Cómo falla, Decisión, Depende de, Trade-off, Relacionado |
| failure sections | `Failure modes…`, `Failure scenarios…`, `Business inconsistencies…` | `Cómo falla…`, `Escenarios de fallo…`, `Inconsistencias de negocio…` |
| sources section | `Sources` | `Fuentes` |
| syllabus line | `Covers from the syllabus` | `Cubre del temario` |

Both corpora have the same boxes, the same `##` sections in the same order, the same number of
cards, failure entries and anti-patterns, and identical cross references (`` `[04, 09]` ``). The
retrieval tests check that parity.

## The web page

`GET /api/v1/i18n/{locale}` serves `ui.json`; the page renders every static text through
`data-i18n` attributes and every dynamic text through a `t(key, params)` helper. The language
switcher stores the choice in `localStorage` and sends it with each chat request.

## Adding a locale

1. Copy `locales/en` to `locales/<xx>` and translate the four files (keep keys and placeholders).
2. Translate `knowledge/en` into `knowledge/<xx>` keeping the structure and the markers you
   declare in `corpus.json`.
3. Add `"<xx>"` to `SUPPORTED_LOCALES` in `mirag/i18n/registry.py`.
4. Run `python -m mirag demo all --locale <xx>`, and compare the keys and placeholders of
   `locales/<xx>` against `locales/en` by hand: the parity tests that used to list anything
   missing went with `tests/`.
